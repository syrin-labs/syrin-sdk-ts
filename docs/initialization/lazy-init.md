> **AI Agent Quick Reference** — The pre-init queue is transparent. You do not need to call any special function to enable it. Just import OpenAI before `init()` and always `await init()`:
> ```typescript
> import OpenAI from "openai";           // ← import first
> import { init } from "@syrin/sdk";
> const openai = new OpenAI();
> const sdk = await init({ apiKey: "..." }); // ← await resolves queue
> ```
> Common mistakes: (1) thinking you need `adapters: ["openai"]` or any configuration to enable queuing — it is automatic; (2) assuming queued events are lost if `init()` fails — the SDK is fail-open, the original LLM calls completed normally, only telemetry is queued.

## Why the Queue Exists

Node.js modules load synchronously. If your module loads OpenAI and runs code at the top level before the async `init()` resolves, those LLM calls happen in the gap between "OpenAI is imported" and "Syrin patch is applied."

Without a queue, those calls would be silently missed. With the queue, the SDK captures the telemetry events and replays them once `init()` finishes.

---

## How It Works

When `init()` starts executing, it sets an internal `isReady = false` flag on `SyrinCore`. The OpenAI patch is applied, but while `isReady` is false, any generated telemetry events are queued in memory instead of being sent to the emitter.

Once `init()` completes all async setup (agent registration, SSE client start, etc.), it calls `core.markReady(emitter)`. This drains the queue — all queued events are forwarded to the emitter and flushed normally.

```
import OpenAI                     ← OpenAI loaded
import { init }                   ← SDK loaded
const openai = new OpenAI()
const sdk = await init(...)       ← isReady = false
    ↳ patchOpenAI()               ← patch applied
    ↳ await core.register()       ← async registration
    ↳ heartbeat.start()
    ↳ sseClient.start()
    ↳ core.markReady(emitter)     ← isReady = true, queue drained
                                  ← all pre-init events flushed here
```

## The Pattern That Triggers the Queue

The queue is most relevant when you call LLM functions at module scope (before your `async main()` function runs):

```typescript
import OpenAI from "openai";
import { init } from "@syrin/sdk";

const openai = new OpenAI();

// This LLM call fires before await init() has a chance to run
// (because module-level code executes synchronously)
const earlyResponse = await openai.chat.completions.create({
  model: "gpt-4o",
  messages: [{ role: "user", content: "Hello" }],
});

// Now init — the earlyResponse event is in the queue
const sdk = await init({ apiKey: "syrin_pk_..." });
// ↑ markReady() fires here — the earlyResponse event is now sent to Syrin
```

In practice, this pattern is unusual. Most applications call `await init()` before any LLM calls. The queue is a safety net for edge cases.

---

## What Gets Replayed

The **telemetry events** generated by the LLM calls are replayed — not the LLM calls themselves. The original calls already executed and returned results to your code. The queue holds `LLM_CALL` events (model, tokens, cost, latency) that would otherwise be lost.

```
Original LLM call:   executes immediately, returns response to your code ✓
Telemetry event:     queued during pre-init window → replayed after init() ✓
```

The LLM response your code receives is unaffected by the queue state.

## The Pre-Init Warning

If you import OpenAI before `init()` and make LLM calls before `await init()` resolves, you will see this warning in the console:

```
[Syrin SDK] ⚠ openai was imported before init() — LLM calls made before this point were NOT instrumented.
Move `await init(...)` to before you construct your OpenAI client to capture all telemetry.
```

This warning fires when `init()` detects that `openai` is already in `require.cache` when `patchOpenAI()` runs. The pre-init queue handles this case — the warning is informational, not an error. The telemetry events are still captured and replayed.

To silence the warning and ensure all calls are captured cleanly, move `await init()` before any LLM calls:

```typescript
import OpenAI from "openai";
import { init } from "@syrin/sdk";

// ✓ Best pattern: init first, then construct client and make calls
const sdk = await init({ apiKey: "syrin_pk_..." });
const openai = new OpenAI();

const response = await openai.chat.completions.create({ ... });
```

## When This Matters

**Mostly harmless scenarios:**

- Your `main()` function calls `await init()` then makes LLM calls — no queue involvement
- Your Express server calls `await init()` at startup before handling any requests — no queue involvement

**Scenarios where the queue fires:**

- Module-level `await openai.chat.completions.create(...)` before `await init()`
- Top-level initialization code that calls LLM functions as part of module loading
- Test files that import and call LLM functions without first awaiting `init()`

In all these cases, the original LLM calls succeed (fail-open), and the queue ensures telemetry is not lost.

---

## Offline Mode and the Queue

When `offline: true`, the queue is still maintained but events are discarded at drain time rather than sent:

```typescript
const sdk = await init({ apiKey: "test", offline: true });
// Queue drains, but events go nowhere — correct behavior for unit tests
```

---

## Diagnostics

To inspect the SDK's ready state programmatically:

```typescript
const d = sdk.diagnose();
// d.connected reflects whether the SDK is in online mode
// d.eventsQueued reflects how many events are waiting for the next flush
```

There is no public API to inspect the pre-init queue directly — it is an internal implementation detail.
